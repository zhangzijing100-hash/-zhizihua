## 1. 界面本身完全可机读

游戏里那个面板（标题「物品详情」）是 **5 列 × 4 行 = 20 格**，每格：

- 左上：一个**三角形图标**（里面是头像）
- 右下：**数字**，白字 + 黑描边，**右对齐**
- 边框颜色按品质分：彩色（UR）/ 金（SSR）/ 紫（SR）/ 蓝（R）

p00 那一页的实际内容：

```
第1行(UR):     7    4    3    6    3
第2行(金):    51   44   64   34   17
第3行(金):    84   38   58   28   31
第4行(金):    34   17  100   21   30
```

**可以滚动**，数字范围 3–221。

## 2. 网格 → 伙伴 的映射（已解出并验证）

顺序规则（用户提供 + 实测验证）：

```
网格 = [你拥有的 UR，按 App 顺序]        ← 只列拥有的，所以长度因人而异，跳过
     + [SSR 块：普通 SSR + 限定 SSR，按 App 的 order 排]
     + [SR 块，按 App order]
     + [R 块，按 App order]
每行 5 格、横向填充
```

自检：**5 UR + 39 SSR + 9 SR + 7 R = 60 = 正好 3 页**。

两条插入规则一格不差命中：
- `零` → `上杉绘梨衣`(限定) → `守夜人`
- `上杉越` → `诺顿`(限定) → `芬里厄`

（App 的 order 里 芬里厄 排在很后面，因为中间夹着 SR/R —— 所以排序必须**先按品质块、再按 order**。）

完整的 60 格顺序表见 `命轮网格-顺序映射.txt`。

## 3. OCR 的做法与踩过的坑

**最终方案：灰度归一化互相关（NCC）模板匹配，完全不做二值化、连通域、切分。**

数字是固定字体、固定位置右对齐渲染的，同一数字每次像素几乎一样；
NCC 对亮度/对比度不敏感，底纹变亮变暗都不影响。
位数（1~3 位）靠「十位/百位槽位是否为空」判断，模板里含一个"空槽位"。

### 踩过的坑（按顺序）

1. **灰度 <78 取黑描边** → 底纹斜纹被吃进来，连通域高度涨到 43，超范围
2. **<50 + 泛洪填内部** → 抗锯齿 1px 缺口会漏；加 1px 膨胀又反过来把整格堵死
3. **固定槽位 + 二值字形匹配** → 数字右对齐得很紧，相邻数字描边渗进下一槽位
   （实测 `171` 的 "7" 渗了 5px），污染字形
4. **只从一个亮底页建模板** → 到了暗底（紫/蓝 SR/R）页**整体对不上**。
   必须亮底 + 暗底 + 过渡行都采模板。**这是最关键的坑。**
5. **行带 top/bottom 会被面板边缘裁切** → 不能直接用 run.top 定位槽位，
   要在 ±14px 范围内搜索「让 5 列最佳 NCC 之和最大」的对齐位置
6. **模板裁剪/去重** → 归一化向量的平方距离阈值要取得很小（NCC>0.99 即 <0.02）；
   取 1.6（相当于 NCC 只有 0.2）会把完全不同的模板当重复，准确率掉到 47%
7. **高通滤波去底纹** → 反而更差（40%）。数字的白填充 vs 黑描边对比本身就是最强特征

最终成绩：训练 3 页 → **100%（80/80 格）**；只用 2 页训练、第三页测试 → **96.3%**。

## 5. 抓取链路（Shizuku）

```
栀子花点「开始读取」
  → 起前台服务 CaptureKeepAliveService（防后台冻结）
  → Shizuku 服务把游戏 am start 到前台
  → 滑动回列表顶部
  → 循环：screencap → 取回 PNG 字节（分片） → 在 App 进程解码裁面板转灰度 → 下一张
  → 切回栀子花
  → JS 端 OCR → 可编辑预览表 → 填入
```

**重要约束：`GameDataUserService`（跑在 shell 进程里）绝对不能碰 android.graphics。**
vivo 给 `BitmapFactory` 的静态初始化挂了钩子
（`android.os.ufw.UltraFrameworkComponentFactory`），shell 进程的 classloader
找不到 `...Impl` 类 —— 实测结果：解码那次调用之后**进程就废了**，
客户端 AIDL 调用永远不返回，App 一直卡在「切换到游戏并截图…」。
所以 shell 侧只跑 `screencap` 拿 PNG 字节，解码放在 App 进程。

## 已经排除的原因（都试过、都有证据）

1. ~~App 切后台被暂停 WebView~~ → 已把整段抓取搬到 Java 后台线程
2. ~~monkey 等游戏 idle 永久阻塞~~ → 改成 `am start`，且所有外部命令带超时
3. ~~shell 进程堆小、解大位图 OOM~~ → 已把解码挪回 App 进程
4. ~~vivo 给 BitmapFactory 加钩子导致 shell 进程废掉~~ → **这个是真的**，
   解码已挪回 App 进程（见上一节）
5. ~~后台应用冻结~~ → 已加前台服务，`dumpsys` 确认 `isForeground=true`，仍卡

## 下次第一步

**强烈怀疑是 `input swipe` 这个命令本身**：它每次都 fork 一个新的 `app_process`
（JVM 启动），在游戏这种重负载下 fork 会阻塞。证据：

- 服务侧日志显示，滑 6~10 次之后就再没有 swipe 记录了
- 但客户端 `callWithTimeout(6000)` 的超时日志也没打出来 —— 说明**整个插件线程**
  都没往下走，不只是那一个 AIDL 调用
- 用户实测反馈：「并没有往下滑，只是在屏幕上点了几下」

**建议的下一步（按优先级）**：

1. **先量准滑动距离**，把滑动次数压到最少。已实测：
   - 快速下滑 500px / 400ms —— 有惯性，**一次就能从最底甩回最顶**
   - 慢速上滑 180px / 900ms —— **正好滚 2 行**（视口 4 行，相邻两张重叠 2 行，好拼）

   ⚠️ **方向别搞反**：`input swipe y1 y2` 里 **y 增大 = 手指下滑 = 内容往早的翻（回顶部）**。
   中途我把方向写反过一次，白费一轮。

2. **换掉 `input`**：考虑 `sendevent` 直接写 `/dev/input/eventX`（不 fork JVM），
   或用 Shizuku 的 `Shizuku.newProcess` 起一个常驻 shell 复用。

3. **实在不行就退一步**：改成「点一次读一页」—— App 截当前页 → 提示用户手动往下滑
   一点 → 再点继续。牺牲自动化换可靠性。
